- **Colab T4 GPU Runner (`scripts/run_colab_t4_experiments.py`):**
  - *AI Generated for Human Execution on Colab T4:* Generated self-contained script `scripts/run_colab_t4_experiments.py` for the user to execute on a Google Colab T4 GPU and return `raw_logs/03_colab_t4_experiments.log` and `raw_logs/03_colab_t4_results.json`.
  - *Human Execution Feedback & AI Bug Fix (SQLite Schema Hallucination):*
    - **What failed:** When the user ran `scripts/run_colab_t4_experiments.py` on Google Colab T4 (which installed `soup-cli 0.77.2` vs. local `0.72.4`), `fetch_latest_run_logs` crashed with `sqlite3.OperationalError: no such column: started_at` on `SELECT * FROM runs ORDER BY started_at DESC LIMIT 1` (and also referenced a hallucinated `training_logs` table instead of `metrics`).
    - **Root Cause & Fix:** Inspected `soup_cli/experiment/tracker.py:21-53` (`_SCHEMA_SQL`). The actual SQLite schema uses `created_at` (not `started_at`) in the `runs` table and stores step-by-step metrics in the `metrics` table (`step, epoch, loss, lr, grad_norm, speed, gpu_mem, timestamp`), not `training_logs`. Updated `fetch_latest_run_logs()` in `scripts/run_colab_t4_experiments.py` to query `runs ORDER BY created_at DESC, rowid DESC LIMIT 1` and `SELECT ... FROM metrics WHERE run_id = ? ORDER BY step ASC`. Also updated the script header to log the dynamically detected `soup_cli.__version__`.
  - *Human Execution Feedback #2 & Real Product Defect Uncovered (False-Positive Hardware-Fit Gate on T4 GPU):*
    - **What happened on Colab T4 (`soup-cli 0.72.4`):** Every `soup train` invocation exited early (`rc=1`, `steps=0`) with:
      `Hardware-fit gate: Predicted peak VRAM 16.2 GB (+10% margin = 17.8 GB) exceeds 15.6 GB available. weights 14.0 | optim 0.1 | grads 0.1 | activations 0.9 | overhead 1.1 GB ... pass --allow-oom-attempt to try anyway.`
    - **Grey-Box Root Cause:** In `soup_cli/utils/gpu.py:169-214`, `model_size_from_name(model_name)` scans the HuggingFace repo ID for `"Nb"` or `"Nm"` substrings and otherwise falls back to `return 7.0` (assuming a 7-billion parameter model = 14.0 GB FP16 weights!). Because `trl-internal-testing/tiny-random-LlamaForCausalLM` (<10 MB actual weights) has no `"Nb"`/`"Nm"` token in its name (just like `gpt2`, `bert-base-uncased`, `distilgpt2`, `facebook/opt-iml-max`, etc.) and `quantization: none` is used, `_hardware_fit_preflight` (`soup_cli/commands/train.py:90-146`) predicts 17.8 GB VRAM and blocks training on a 15.6 GB Colab T4 GPU!
    - **Fix Applied to Script:** Updated `scripts/run_colab_t4_experiments.py` to: (a) capture one unflagged run (`hardware_fit_gate_false_positive_without_flag`) as raw empirical evidence of this false-positive gate defect, and (b) pass `--allow-oom-attempt` on all subsequent `soup train` calls so the real T4 GPU training steps execute and record loss curves and adapter weights.
  - *Human Execution Feedback #3 & Real Product Defect Uncovered (Default `bf16=True` Crash on NVIDIA Tesla T4 GPU):*
    - **What happened on Colab T4:** With `--allow-oom-attempt` enabled, default `soup train` failed on Tesla T4 (`cc=7.5`, Turing architecture) because `SFTTrainerWrapper._resolve_mixed_precision` (`soup_cli/trainer/sft.py:708-716`) returns `(self.device == "cuda", False)` whenever `tcfg.auto_mixed_precision` is `False` (the default in `TrainingConfig`!). This unconditionally sets `bf16=True` in `transformers.TrainingArguments` on all CUDA GPUs—even though Turing T4 (`cc=7.5`) does not support `bf16` (which requires Ampere `cc>=8.0`). Meanwhile, `soup_cli/utils/gpu.py:216-228` (`get_compute_dtype()`) properly checks `torch.cuda.is_bf16_supported()`, and `pick_mixed_precision()` (`sft.py:729`) checks `cc`, but `_resolve_mixed_precision` skips both unless the user manually sets `auto_mixed_precision: true`!
    - **Fix Applied to Script:** Updated `make_base_config()` in `scripts/run_colab_t4_experiments.py` to include `"auto_mixed_precision": True` so all training runs use `fp16` on T4, and added a dedicated pre-probe (`default_bf16_crash_on_t4_without_auto_mixed_precision`) with `auto_mixed_precision=False` to capture the exact default-config T4 crash in `raw_logs/03_colab_t4_results.json`.
  - *Human Execution Feedback #4 & Base Model `chat_template` Requirement (`sft_format.py:183`):*
    - **What happened on Colab T4:** After bypassing the Hardware-Fit gate (`--allow-oom-attempt`) and setting `auto_mixed_precision: true`, `soup train` reached dataset tokenization and raised `ValueError: Tokenizer has no chat_template. Pass data.chat_template: chatml ... in soup.yaml` (`soup_cli/data/sft_format.py:71-83, 183-189`). Note that `soup train --dry-run` did NOT catch this because `--dry-run` (`commands/train.py:1210-1217`) exits before loading the tokenizer or calling `build_format_row()`!
    - **Fix Applied to Script:** Updated `make_base_config()` and `CHATML_SAMPLE_ROWS` in `scripts/run_colab_t4_experiments.py` so every generated training config sets `data.format: "chatml"` and `data.chat_template: "chatml"` while preserving `training.auto_mixed_precision: true` and `--allow-oom-attempt` on every `soup train` call.

## Phase 4 (Empirical Colab T4 Analysis, Bug Triage & Final Deliverables)
- **Empirical Colab T4 Logs Returned by User (`raw_logs/03_colab_t4_experiments.log`, `raw_logs/03_colab_t4_results.json`):**
  - *Human Executed on Google Colab Tesla T4 GPU:* The user ran `scripts/run_colab_t4_experiments.py` on a Tesla T4 (`Python 3.13.16`, `PyTorch 2.14.1+cu130`, `CUDA 13.0`, `cuDNN 92800`, `soup-cli 0.72.4`) and returned the untouched 666-line log and 1,463-line JSON metrics file.
  - *AI Mathematical & Grey-Box Root Cause Discovery from Real GPU Data:*
    - When inspecting `raw_logs/03_colab_t4_results.json`, we noticed a striking paradox: in Exp 1A (`seed=42` vs `seed=42`), the step-by-step loss curves matched to within `0.0006`, yet the saved adapter weights had `global_l2_diff = 4.729505`!
    - By inspecting the per-tensor norms (`lora_A` L2 diff $\approx 2.30\text{--}2.46$ vs `lora_B` L2 diff $\approx 0.02\text{--}0.04$) and tracing `SFTTrainerWrapper.setup()` (`soup_cli/trainer/sft.py:219, 471, 949`), we proved mathematically and structurally that `get_peft_model()` runs at line 949 **before** `TrainingArguments` sets `seed=42` at line 471. Thus `lora_A` is initialized from unseeded OS entropy on every run ($\sqrt{\|A_1\|_2^2 + \|A_2\|_2^2} \approx 2.33$), while DataLoader batch order is seeded by `TrainingArguments`!
    - In SF-GPU-2 (`lr: 1e15`), the real T4 log revealed that even when `loss_watchdog` triggers at Step 1/15 (`Epoch 0.2/3`) and halts training with `lora_B` exploded to $2.26 \times 10^{16}$, `soup train` still prints `Training Complete!`, marks the SQLite run `"completed"`, and exits with code `0`.
  - *AI Test Parser Adjustments Preserved:* Updating `test_repro03_parse_colab_t4_results_if_available` in `tests/test_reproducibility.py` took two schema-key adjustments (`run1["cli"]["returncode"]` and `weight_comparison`), preserved untouched in `raw_logs/03_reproducibility_local_run2_failed.log` and `raw_logs/03_reproducibility_local_run3_failed.log` before passing (`3 passed` in `raw_logs/03_reproducibility_local.log`).
